# Repository guide

This repo is a Home Manager flake with workstation (`workstation` on Manjaro/Sway, `workstation-nixos` on NixOS/Sway, `workstation-darwin` terminal-only) and deployment (`deploy`, minimal x86_64 Linux) setups. `main.nix` selects app modules under `profiles/`; Sway and LibreWolf are Linux workstation-only. **Every app should have its own `profiles/<app>/main.nix` module**, with any app-specific config files alongside it. Keep `main.nix` for composing profiles and shared settings rather than adding app configuration there. LibreWolf and the Manjaro NetworkManager client use the separately pinned `browser-nixpkgs` input; NixOS NetworkManager stays on main `nixpkgs`. Avoid putting credentials or writable browser-profile data in the Nix store. Home Manager only exposes `nmcli` on the workstation; Manjaro's NetworkManager daemon remains host-managed. Never restart or update the live daemon automatically during a Home Manager switch.

## Applying changes on this desktop

- From the repo root, use `home-manager switch --flake .#workstation` to activate a change. Editing files or building a generation alone does not update the running session. Don't switch configurations or restart apps merely to test without checking with the user.
- `profiles/sway/config` becomes `~/.config/sway/config`. Sway does **not** reload automatically on a Home Manager switch. After changing Sway configuration or a store-pinned script referenced by a Sway binding, press **Super+Shift+C** (or start a new Sway session). The loaded Super+1 binding otherwise can still point at an older script derivation.
- Super+1 runs `profiles/sway/browser-workspace-one.sh` via the `browserWorkspaceOne` wrapper in `profiles/sway/main.nix`. It moves/focuses an existing LibreWolf window on workspace 1; only if none exists does it launch one. The script's browser argument is the stable `~/.local/state/nix/profiles/home-manager/home-path/bin/librewolf` link, not a pinned browser store path. A browser package update changes the target for **future launches**, not a running browser process.
- `profiles/librewolf/main.nix` defines policies and preferences. After activating LibreWolf policy, preference, or package changes, **fully quit LibreWolf**, then press Super+1 to launch it again. Super+1 alone does not restart or reload it. Do not automatically kill the browser on activation: that risks open tabs and sessions. The existing XDG browser profile is writable and must not be replaced by Home Manager; only the overrides file is linked into it.
- **LibreWolf add-on lesson:** Setting `policies.ExtensionSettings.<addon-id> = { installation_mode = "normal_installed"; install_url = "https://addons.mozilla.org/.../latest.xpi"; };` evaluated and appeared in the built browser's `policies.json`, but Vimium-FF was not installed after a restart. Evaluating a policy is not proof that the add-on installs. The working approach here is a hash-verified, signed AMO XPI fetched into the Nix store and installed with `policies.Extensions.Install`. This was verified by launching the newly built browser against a separate temporary profile and checking `extensions.json` for the active add-on; do not test against or replace the user's live profile. A remote AMO URL in `Extensions.Install` also failed in a temporary profile; the cause of the remote-download failures was not established. Firefox runs `Extensions.Install` once per policy change: the XPI is a reproducible installation bootstrap, **not** a runtime version pin. Keep add-on auto-updates enabled so LibreWolf can update it in its writable profile; updating the bootstrap XPI itself requires a URL/hash change.
- `profiles/tmux/main.nix` includes `profiles/tmux/tmux.conf` via `programs.tmux.extraConfig` (and adds `SWAYSOCK` on workstation). Switching Home Manager updates the generated `~/.config/tmux/tmux.conf`, **not** an already-running tmux server. Reload it with **Ctrl+A, r** or `tmux source-file ~/.config/tmux/tmux.conf` after tmux config changes.
- The tmux config adds `SWAYSOCK` to `update-environment`: reattaching from a terminal with the current socket updates tmux's environment for future panes. Existing shells keep their own environment. If `swaymsg` fails, check whether `$SWAYSOCK` points to a live socket in `$XDG_RUNTIME_DIR`; a shell or tmux pane can retain the socket from an older Sway session. Super+Shift+C is a compositor binding and does not depend on a stale terminal's `SWAYSOCK`.

When checking whether a Sway change is live, compare the Super+1 line from `swaymsg -t get_config` with `~/.config/sway/config`. If the current shell's `SWAYSOCK` is stale, pass the live socket explicitly with `swaymsg -s /path/to/live/sway-ipc.sock ...`; don't conclude that Sway is down merely because this shell's `swaymsg` cannot connect.
